## 实现顺序

1. **0.3.5 反馈功能**：允许用户在软件内整理并提交问题、建议和必要的诊断资料。
2. **0.3.6 Git 协同适配**：识别 Git 仓库资源并提供安全、明确的协同工作流。
3. **0.3.7 局域网聊天**：为已连接设备提供点对点文字会话、通知和资源引用。
4. **0.4.x 程序存储位置与磁盘空间**：确定客户端所有持久数据和临时数据放在哪里。
5. **0.5.x 资源树与访问权限**：建立稳定的资源组织方式和设备身份校验。
6. **0.6.x 多服务器连接**：复用前两项的存储、资源树、身份和权限模型。
7. **GitHub 差分更新（版本待定）**：仅在公网完整包分发量或带宽成本有明确需求时再排期，不阻塞以上功能。

服务器功能依赖存储位置与权限模型。若先做服务器，上传缓存、服务端文件树、用户身份和白名单都会重复改造。当前局域网内由可信设备发布最新完整版本即可满足升级需求，因此不为差分更新延后这些基础功能。

## 已完成：0.3.3 设备备注、资源备注与定向提醒

提醒只表达“建议下载这个资源”，不能绕过接收方确认、替接收方选择保存位置或自动写入文件。第一版只通过当前点对点连接即时送达，不实现离线消息队列。

## 0.3.6 去中心化 Git 协作

### 已实现的第一阶段

每台设备保管自己的 Git 仓库、签名密钥和追加式协作线。A 创建项目后，B、C 可各自克隆；B 从 A 的提交分叉，C 从 B 的提交同步，都会在协作图中留下各自的点和连线。设备相遇时交换缺失的签名记录，任何在线成员都可转发其他成员的记录；A 离线时 B、C 仍能协作，之后再补齐。代码包与协作图记录分开复制和校验，不要求 A 永久在线。

- [x] 独立“Git 协作”分页；检测 Git，缺失时提供 WinGet 一键安装、手动选择 `git.exe` 和官方下载入口。
- [x] 选择本地仓库创建项目；仅发布已提交历史，显示未提交修改提醒；仓库根目录、分支、HEAD 和 Git 版本由 Git 命令核验。
- [x] 每台设备只签署自己的追加式协作记录，限制事件大小与链顺序；记录按成员序号互相补齐，能经第三台设备转发。
- [x] 使用完整 Git bundle 发布提交；加入时下载并克隆，选中协作点时下载到收件箱引用。只有可快进且工作树干净时才自动同步；分叉需用户在 Git 工具中自行合并。
- [x] 协作包最多 1 GB，支持 HTTP Range 续传与 SHA-256 校验；不发送本地 Git 远端 URL、配置或凭据。
- [x] 普通文件夹分享排除 `.git`；选中分支历史中的 Git LFS 对象与 Git bundle 一起打包并逐个核验、导入。子模块、稀疏检出和浅克隆暂不支持一键协作。
- [x] A/B/C 离线后补齐、签名篡改拒绝、局域网传包续传及 `.git` 隔离有自动化测试。

## 0.3.7 局域网聊天

### 目标

已连接设备之间可以在局域网内进行一对一文字聊天和资源卡片传送。会话以固定设备 ID 关联；离线消息保存在发送方本机，双方重新在线后自动补发。历史仅存各自电脑，不经服务端或跨设备同步。

### 0.3.7 消息协议与存储

- [x] 新增 `chat-v1` 点对点协议，包含固定消息 ID、发送方与接收方设备 ID、发送时间和文字或资源 ID。
- [x] 接收端核对已登记的设备 ID 与来源入口；请求体上限 16 KiB，文字上限 2,000 字，每台设备每分钟最多 60 条。
- [x] 消息以发送设备 ID 与消息 ID 去重，接收端落库后才确认；确认丢失的重试不会生成第二条消息。
- [x] SQLite 保存会话、未读游标、静音期限与待发状态；移除设备时可保留或删除历史，本机也可手动清空会话。
- [x] 离线消息本机排队，15 秒起退避至最多 5 分钟；7 天未送达后停止自动发送，手动重试保留原消息 ID。

### 0.3.7 聊天界面与通知

- [x] “聊天”位于 Git 协作之后，左侧列出设备、在线状态和未读数，右侧显示消息时间线、输入框与发送按钮。
- [x] 会话以设备 ID 关联；对方修改昵称、IP 或端口后仍进入原会话。
- [x] 不在当前会话时弹出右下角 5 秒通知并增加未读；点击通知打开对应会话。
- [x] 支持对单台设备静音 1 小时、清空本地会话；静音只影响提示，不影响消息接收和未读记录。
- [x] 按会话有序补发，不阻塞其他设备；失败时退避而不是高频重试。
- [x] 界面明确提示局域网 HTTP 聊天没有端到端加密，不适合传送敏感信息。

### 0.3.7 资源引用

- [x] 对聊天版本的“发送给”一次投送一张持久资源卡片并弹出通知；旧版设备保持一次性提醒。
- [x] 用户可以从自己已发布且当前可用的资源生成卡片，离线时排队并在真正发送前重新核对。
- [x] 接收方点击资源卡片时重新读取发布方目录并核对资源 ID 与可用状态，再进入现有下载流程。
- [x] 第一版不提供任意聊天附件；需要发送文件时先发布为资源，再发送资源卡片。
- [x] 资源撤销或发布方离线后历史卡片仍保留，点击下载时显示当前不可下载原因。

## 已实现：0.4.x 程序存储位置与磁盘空间

### 目标

用户可以选择 ResourceManager 的程序数据目录，避免数据库、复制发布的资源、更新包和临时文件持续占用系统盘。首次使用时必须确认存储位置，之后可以在设置中迁移。

界面统一使用“存储位置”这个名称，因为其中既有可清理的缓存，也有数据库、发布副本等不可随意删除的数据。

### 0.4.0 存储目录基础

- [x] 增加启动引导：首次打开时显示存储位置选择窗口，用户确认后再进入主界面。
- [x] 列出本机固定磁盘，并显示每个磁盘的总容量与剩余空间；允许手动选择具体文件夹，确认时验证所选目录可读写。
- [x] 默认建议 `%LOCALAPPDATA%\ResourceManager`，但不替用户自动确认。
- [x] 在写入配置前验证目录可创建、可读写，且不是某个普通文件的子路径冲突。
- [x] 使用一个很小的引导配置记录实际数据目录；数据库和大文件写入用户选择的位置。
- [x] 将以下内容统一放入存储根目录：
  - SQLite 数据库及 WAL 文件；
  - “复制到软件管理目录”的发布副本；
  - 软件更新暂存包；
  - 日志；
  - 下载任务状态和软件内部临时缓存。
- [x] 用户主动选择的下载目标继续保存在用户指定的位置，不强制放进程序存储目录。
- [x] 下载目标旁的 `.rm-part` 仍跟随用户选择的目标目录，避免跨磁盘完成下载时再次复制整个文件；数据库中的断点状态放在程序存储目录。
- [x] 所选磁盘断开、目录丢失或权限变化时，阻止服务带着空数据库启动，并给出重新选择或重试入口。

### 0.4.1 修改位置与安全迁移

- [x] 设置页增加“存储位置”，显示当前绝对路径并允许更改。
- [x] 检测旧版 `%LOCALAPPDATA%\ResourceManager` 数据；首次进入新版时提供迁移，而不是创建一套空数据。

## 0.6.x 多服务器连接、发布与上传

### 目标

`ResourceManager.Server 0.0.1` 已先提供 Windows x64 反馈服务和仅限本机访问的浏览器管理页。0.6.x 继续复用该 ASP.NET Core 服务端基础，并在加入资源能力时补充 Linux x64、systemd 和容器产物；服务端核心不能依赖 WPF、WinForms 或 Windows 注册表。

客户端可以：

- 绑定多台部署了 ResourceManager 服务端的服务器；

- 浏览同一服务器中其他用户允许访问的资源；
- 发布本机资源入口，文件内容仍由发布方电脑提供；
- 把资源上传到服务器，发布方离线后仍可从服务器下载。

### 客户端更新流程

- [x] 下载更新时先计算当前正在使用的 EXE SHA-256；只有版本和旧文件哈希都与更新清单一致时才允许使用差分包。
- [x] 优先下载匹配当前版本的差分包；没有匹配补丁、用户跨版本升级或旧文件被修改时自动下载完整 EXE。
- [x] 差分包和完整包使用持久临时文件与 HTTP Range 断点续传；来源不支持续传时重新下载。
- [x] 大文件请求不再发送 `Cache-Control: no-cache`；仅最新版本元数据请求使用重新验证策略。
- [x] 在临时位置用旧 EXE 应用补丁，不修改正在运行的正式 EXE。
- [x] 补丁生成的新 EXE 必须同时通过目标文件大小、SHA-256、`MZ` 文件头和目标版本检查；任一检查失败时删除临时结果并自动回退完整包。
- [x] 所有校验通过后继续沿用当前退出旧进程、替换和重新启动流程；数据库、设备 ID、发布、收藏和下载任务保持不变。
- [x] 更新界面显示下载方式、已下载大小、实时速度和预计剩余时间，并明确标记“差分更新”或“完整更新”。

### 第一版支持范围

- [x] 只保证从最新上一正式版本升级到当前目标版本，不串联多个历史补丁。
- [x] 从更早版本直接升级时使用完整包。
- [x] 保留桌面手工下载完整 EXE 的方式，差分系统故障不能阻止用户正常安装最新版。

### 验收场景

- [ ] 当前 EXE 哈希不匹配、补丁损坏、补丁应用失败和新 EXE 校验失败时，旧程序保持可用并自动切换完整包。

## 开始实现前需要逐项确认的选择

这些问题不阻塞记录需求，但进入对应版本前需要确定：

1. 存储位置是否包含日志和更新暂存包。当前建议包含，系统盘只保留很小的目录指针。
2. 资源分组是否允许无限层级。当前建议支持多级，但界面限制常用操作保持简单。
3. 白名单是否只授权设备，还是未来也支持服务器账号和用户组。0.5.x 先按设备 ID，服务器阶段再扩展主体类型。
4. 已确认：同一局域网或已配置直连连接时走直连；不同局域网且未配置直连连接时走服务器中继。普通资源和客户端更新包遵守同一规则。
5. 已确认：服务器采用公网 HTTPS 地址直接加入，自动登记设备身份并签发短期会话令牌，不要求邀请码或账号。
6. 已确认：上传模式第一版不设配额、单资源大小上限、固定容量预留或保留期限，后续有需要再增加；保留磁盘不足及写入失败处理。后续用户已授权一次完成剩余服务端开发：同名文件独立保存，不自动覆盖；所有者或管理员明确删除资源，不自动清理。
7. 反馈提交渠道使用自建接口、GitHub Issues 中转还是其他服务。当前建议客户端依赖抽象提交接口，并始终保留本地导出反馈包。
8. Git 协同第一版采用 Git bundle、临时只读 Git 服务还是工作树快照。当前建议 Git bundle，边界清楚且不需要在客户端托管写操作。
9. 局域网聊天未来是否需要服务器离线消息、跨设备历史同步和端到端加密。0.3.7 第一版建议只做在线点对点消息与本机历史。

## 暂不纳入以上版本

- 公网 NAT 打洞；
- 多服务器联邦；
- 端到端加密；
- 自动把发布资源同步成多设备副本；
- 未经用户确认的旧数据自动删除。
