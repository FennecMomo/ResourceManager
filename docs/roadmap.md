# ResourceManager 开发待办与版本路线

> 状态：需求池 · 最后更新：2026-09-23 · 当前发布版本：0.3.2 · 当前开发版本：0.3.3 · 下一功能版本：0.3.4

本文记录已经提出、尚未实现的需求。后续按依赖关系逐项完成，每一项都应独立构建、测试和验收，不要求在一个版本中同时交付。

## 当前安排：0.3.2 局域网更新源与安装稳定性

当前使用场景以局域网分发为主：由一台可信设备发布最新的完整 `ResourceManager.exe`，其他已连接设备优先从局域网下载。GitHub 差分更新不再作为 0.3.2 或近期版本的前置目标，完整方案保留在路线末尾，等公网分发量或带宽成本确实需要时再实施。

- [x] 已连接设备发布的 `ResourceManager.exe` 可作为局域网更新源，并公开内嵌版本、大小和 SHA-256。
- [x] 接收端同时检查 GitHub 和局域网来源；同版本本地副本必须与 GitHub 官方摘要一致。
- [x] GitHub 尚未确认的局域网更高版本不会自动安装，手动更新时必须确认信任发布设备。
- [x] 下载完成后重新核对大小、SHA-256 和 `MZ` 文件头，再进入安装流程。
- [x] 安装助手等待原进程退出和单实例互斥锁释放后再替换并重启，同时兼容旧版安装参数。
- [x] 局域网来源失败且 GitHub 存在同版本时自动回退 GitHub 完整包。
- [ ] 发布 `v0.3.2` 正式完整 EXE，并用 `0.3.1 → 0.3.2` 做一次真实升级验收。

## 已完成：0.3.1 路由器入口与 UPnP 扩展发现

- [x] 外层设备手动保存路由器 WAN IPv4，只扫描固定范围 `48001–48099`。
- [x] 刷新时优先验证缓存端口；发现快照中存在未知设备时才补扫未检查端口。
- [x] 引导节点通过 UDP `37643` 发现内部设备，目标设备只为自己创建 UPnP 映射。
- [x] 支持长期映射、有限租期续租、五分钟验证、启动恢复和用户显式删除。
- [x] 同一 WAN IP 支持多个设备端点，收藏继续绑定固定设备 ID。
- [x] 设置页显示路由器 LAN/WAN 地址、实际网卡、UPnP 与本机外部端口。
- [x] 下载直接连接目标设备，不通过引导节点传输。

该功能没有占用 0.4.x 编号，后续存储位置路线保持不变。

## 实现顺序

1. **收口并发布 0.3.2**：验证局域网完整包升级、安装替换和自动回退链路。
2. **0.3.3 设备备注、资源备注与定向提醒**：补充局域网协作信息，并允许发布方提醒指定设备下载某个资源。
3. **0.3.4 反馈功能**：允许用户在软件内整理并提交问题、建议和必要的诊断资料。
4. **0.3.5 Git 协同适配**：识别 Git 仓库资源并提供安全、明确的协同工作流。
5. **0.3.6 局域网聊天**：为已连接设备提供点对点文字会话、通知和资源引用。
6. **0.4.x 程序存储位置与磁盘空间**：确定客户端所有持久数据和临时数据放在哪里。
7. **0.5.x 资源树与访问权限**：建立稳定的资源组织方式和设备身份校验。
8. **0.6.x 多服务器连接**：复用前两项的存储、资源树、身份和权限模型。
9. **GitHub 差分更新（版本待定）**：仅在公网完整包分发量或带宽成本有明确需求时再排期，不阻塞以上功能。

服务器功能依赖存储位置与权限模型。若先做服务器，上传缓存、服务端文件树、用户身份和白名单都会重复改造。当前局域网内由可信设备发布最新完整版本即可满足升级需求，因此不为差分更新延后这些基础功能。

## 0.3.3 设备备注、资源备注与定向提醒

### 目标

用户可以为已经连接的设备保存本机备注，发布方可以为自己发布的资源添加说明，并可以选择某个已发布资源向指定的在线设备发出提醒。接收方直接看到提醒弹窗，并可从弹窗进入现有下载流程。

提醒只表达“建议下载这个资源”，不能绕过接收方确认、替接收方选择保存位置或自动写入文件。第一版只通过当前点对点连接即时送达，不实现离线消息队列。

### 0.3.3 设备备注

- [ ] 在设备记录中增加本机备注字段，以固定设备 ID 为关联键；设备修改昵称、IP 或端口后备注仍然保留。
- [ ] 备注仅保存在填写者本机，不发送给对方，也不改变对方声明的设备昵称。
- [ ] 允许在设备页新增、修改和清空备注；限制长度并按纯文本处理。
- [ ] 设备列表优先显示对方昵称，同时在副标题或详情中显示备注，避免备注被误认为对方真实名称。
- [ ] 删除设备时一并删除本机保存的设备备注，并在确认提示中说明。
- [ ] 旧数据库升级后已有设备的备注为空，不影响设备、端点和收藏记录。

### 0.3.3 发布资源备注

- [ ] 在本机发布资源记录和远端资源目录模型中增加发布方备注字段，以资源 ID 为关联键。
- [ ] 发布方可以在“我的发布”页面新增、修改和清空资源备注；备注限制长度并按纯文本处理。
- [ ] 资源备注随资源目录返回给已连接设备，并在设备资源列表、收藏详情和下载确认界面中展示。
- [ ] 修改备注只更新资源元数据，不改变资源 ID、发布时间、源文件位置或现有收藏。
- [ ] 撤销发布时一并删除备注；重新发布同一路径会生成新资源和空备注，不自动继承旧备注。
- [ ] 与旧版节点互通时，将缺失的备注视为空字符串，不影响目录浏览和下载。

### 0.3.3 定向资源提醒

- [ ] 发布方从“我的发布”中选择一个当前可用的资源，再选择一台已连接且在线的目标设备发送提醒。
- [ ] 新增点对点提醒协议，至少包含发送方设备 ID、资源 ID、资源名称、资源类型、资源备注和发送时间；限制字段长度和请求体大小。
- [ ] 接收端必须确认请求来自已经握手并登记的设备，并重新从发送方目录核对资源 ID、可用状态和展示信息，不能直接信任提醒正文。
- [ ] 接收提醒后，即使主窗口缩到托盘也直接显示置顶提醒弹窗；弹窗明确显示发送设备、资源名称、类型和备注。
- [ ] 弹窗提供“下载资源”“稍后处理”和“关闭”操作；“下载资源”打开保存位置选择并复用现有 `DownloadManager` 创建普通下载任务。
- [ ] 发送方不能替接收方选择路径、不能自动开始写入文件，也不能通过提醒绕过资源可用性和后续权限检查。
- [ ] 目标设备离线、地址变化、资源已撤销或请求被拒绝时，发送方显示明确失败原因，不记录为发送成功。
- [ ] 对重复提醒进行短时间去重并设置发送频率限制，避免同一设备连续弹窗；接收方可以对单台设备临时静音提醒。
- [ ] 第一版不保存服务器端或发布方离线队列；发送时目标不在线就直接失败，后续重新发送必须由用户主动操作。
- [ ] 提醒弹窗关闭或选择“稍后处理”后，在本机保留一条可再次打开的提醒记录；资源撤销或发布方离线时显示相应状态。

### 验收场景

- [ ] 给设备添加备注后，设备改昵称和地址仍显示原备注；另一台设备看不到这条本机备注。
- [ ] 发布方修改资源备注后，对方刷新目录即可看到，原收藏仍指向同一资源 ID。
- [ ] 发布方选择在线设备发送提醒后，对方在主窗口打开和缩到托盘两种状态下都能看到弹窗。
- [ ] 对方点击“下载资源”后可以选择保存位置，并在下载页看到与普通资源下载一致的进度、暂停和失败状态。
- [ ] 对方关闭提醒、选择稍后处理或静音发送方时，不会自动产生下载文件。
- [ ] 伪造设备 ID、未知来源 IP、已撤销资源和篡改资源名称的提醒均不会进入可下载状态。
- [ ] 旧版节点仍可连接和下载资源，但不会显示备注，也不参与提醒协议。

## 0.3.4 反馈功能

### 目标

用户可以在软件内提交问题、改进建议和使用体验反馈，并自主决定是否附带版本、系统环境、日志或截图。提交失败时保留草稿和明确状态，不因为反馈服务不可用影响资源共享主流程。

### 0.3.4 反馈内容与界面

- [ ] 在设置或帮助区域增加“反馈”入口，支持“问题”“建议”“体验”和“其他”分类。
- [ ] 反馈正文必填并限制长度；联系方式选填，明确说明其用途和可见范围。
- [ ] 自动填写 ResourceManager 版本、协议版本和 Windows 版本，但在提交前向用户展示。
- [ ] 日志、截图、设备 ID、网络地址和诊断信息全部采用显式勾选，不默认附带潜在敏感信息。
- [ ] 提交前提供最终预览，允许删除单个附件，并对访问令牌、带凭据 URL、本机用户名和绝对路径进行检测与提醒。
- [ ] 支持保存本地草稿；关闭窗口或提交失败不会丢失尚未发送的正文。

### 0.3.4 提交与状态

- [ ] 在实现前确定正式提交渠道，并通过独立接口封装，避免界面直接依赖 GitHub、邮箱或某个固定服务。
- [ ] 至少提供一个可用的在线提交渠道，并保留“导出反馈包”作为离线或服务故障时的备用方式。
- [ ] 限制附件类型、单文件大小、总大小和请求超时；反馈包使用可检查的普通格式，不包含可执行文件。
- [ ] 清楚显示“草稿”“正在提交”“已发送”“发送失败”和“已导出”，失败时可以重试但不能重复创建多份相同反馈。
- [ ] 提交使用独立取消令牌和后台任务，不阻塞共享服务、下载和主界面。
- [ ] 客户端不内置可用于管理反馈平台的高权限令牌，日志中不记录反馈正文、联系方式或附件内容。

### 验收场景

- [ ] 只填写正文即可成功提交；选择附带日志时，预览与实际反馈包内容一致。
- [ ] 用户未勾选诊断资料时，提交内容不包含设备 ID、IP 地址、日志和本机路径。
- [ ] 网络断开、服务超时和附件过大时给出明确错误并保留草稿，恢复后可以重试。
- [ ] 反馈服务不可用时，设备连接、资源浏览和下载继续正常工作。
- [ ] 导出的反馈包可以由用户自行检查内容，再通过其他渠道发送。

## 0.3.5 Git 协同适配

### 目标

当发布的文件夹是 Git 仓库时，ResourceManager 能识别其协作状态并提供安全的交付方式，让接收方清楚知道仓库、分支、提交和未提交修改的状态。第一版不把 ResourceManager 做成完整 Git 托管平台，也不替用户自动执行 push、merge、rebase 或 reset。

### 0.3.5 仓库识别与展示

- [ ] 检测发布目录是否位于 Git 工作树中，并解析仓库根目录、当前分支、HEAD 提交、工作树是否干净以及 Git 版本。
- [ ] 在发布方和接收方资源详情中显示分支、短提交号、提交时间和“存在未提交修改”等状态。
- [ ] 远端 URL 展示前移除用户名、密码、访问令牌和查询参数；默认不向其他设备公开完整远端地址。
- [ ] Git 命令使用参数列表调用并设置超时、取消和输出上限，不拼接可执行的 Shell 命令。
- [ ] 没有安装 Git、仓库损坏、处于 detached HEAD 或命令超时时，回退为普通文件夹资源并显示原因。

### 0.3.5 安全发布与获取

- [ ] 普通文件夹下载默认排除 `.git` 元数据，避免泄露远端凭据、配置、hooks、reflog 和不可达历史对象。
- [ ] 在实现前确定 Git 协同的主要交付形式：生成 Git bundle、提供临时只读 Git 服务，或只传递工作树快照；默认建议第一版使用 Git bundle。
- [ ] 若使用 Git bundle，发布方在临时位置生成只读包并记录目标提交、分支和 SHA-256，接收方可选择新建仓库或导入已有仓库。
- [ ] 未提交修改不能悄悄混入“干净提交”交付；用户必须明确选择仅交付已提交历史，或额外生成工作树变更包。
- [ ] 子模块、Git LFS、稀疏检出和超大仓库必须显示支持状态；第一版不支持的情况应阻止误导性的一键导入。
- [ ] Git 交付复用现有资源下载、进度、暂停、续传和校验流程，不另建不受约束的文件传输通道。
- [ ] 接收完成后只提供明确的 clone/fetch/import 操作；任何会覆盖本地修改或改写历史的动作都必须由用户在 Git 工具中确认。

### 验收场景

- [ ] 发布干净仓库后，对方看到的分支和提交号与发布方一致，并能导入得到同一 HEAD。
- [ ] 普通文件夹方式下载 Git 仓库时不包含 `.git` 目录和其中的远端凭据。
- [ ] 仓库有未提交修改时界面明确提示，选择“仅已提交内容”不会把修改意外发送给对方。
- [ ] 含凭据的 HTTPS 远端和 SSH 地址不会出现在远端目录、日志或提醒消息中。
- [ ] Git 未安装、bundle 损坏、目标目录已有未提交修改和磁盘空间不足时，不会破坏接收方已有仓库。

## 0.3.6 局域网聊天

### 目标

已连接设备之间可以在局域网内进行点对点文字聊天。会话以固定设备 ID 关联，支持未读提示、托盘通知、消息状态和资源引用；第一版不依赖中心服务器，不提供跨公网中继，也不承诺离线送达。

### 0.3.6 消息协议与存储

- [ ] 新增版本化的点对点聊天协议，消息至少包含消息 ID、发送方设备 ID、接收方设备 ID、发送时间、类型和正文。
- [ ] 接收端必须确认来源已经握手并与已保存设备 ID 匹配；未知来源、设备 ID 冲突和超大请求直接拒绝。
- [ ] 文本按纯文本处理，限制单条长度、发送频率和请求体大小，不解析 HTML、脚本或可执行富文本。
- [ ] 消息使用唯一 ID 去重，并返回“已送达”确认；发送方区分“发送中”“已送达”和“发送失败”。
- [ ] 本地保存会话历史和未读状态；删除设备前提示是否同时删除聊天记录。
- [ ] 第一版只在双方在线时发送，目标离线立即标记失败；离线队列和服务器同步留到服务器版本后再决定。

### 0.3.6 聊天界面与通知

- [ ] 增加“聊天”工作区，左侧列出已连接设备及未读数量，右侧显示当前会话时间线和输入框。
- [ ] 会话以设备 ID 关联；对方修改昵称、IP 或端口后仍进入原会话，界面同步展示最新昵称和本机设备备注。
- [ ] 主窗口缩到托盘时，新消息通过托盘通知和窗口内未读标记提示；点击通知打开对应会话。
- [ ] 支持对单台设备静音、清空本地会话和复制消息文本；静音只影响提示，不影响消息接收和未读记录。
- [ ] 聊天失败不能阻塞设备状态刷新、资源下载或共享服务，连续失败采用退避而不是高频重试。
- [ ] 明确提示局域网聊天的信任边界；第一版不宣称端到端加密，敏感信息不应通过未受信网络发送。

### 0.3.6 资源引用

- [ ] 0.3.3 的定向资源提醒在聊天时间线中表现为结构化“资源卡片”，同时保留直接提醒弹窗能力。
- [ ] 用户可以从自己已发布且当前可用的资源生成卡片发送给一台在线设备。
- [ ] 接收方点击资源卡片时重新向发布方核对资源 ID、名称、类型、备注和可用状态，再显示下载操作。
- [ ] 第一版不提供任意聊天附件；需要发送文件时先发布为资源，再发送资源卡片，统一复用现有权限和下载模型。
- [ ] 资源撤销、发布方离线或未来失去权限后，历史卡片保留但明确显示不可下载原因。

### 验收场景

- [ ] 两台在线设备可以互发中英文和多行纯文本，消息顺序、送达状态和未读数量正确。
- [ ] 应用在前台、最小化和缩到托盘时均能收到消息；静音设备不会弹出提示但消息仍进入会话。
- [ ] 对方更换地址和昵称后聊天历史不丢失，也不会错误合并到另一设备。
- [ ] 断网、目标离线、重复请求和伪造设备 ID 时不会产生重复消息或假“已送达”状态。
- [ ] 资源卡片只能引用发送方真实发布且当前可访问的资源，接收方确认后才能选择保存位置并下载。
- [ ] 新版与旧版节点继续完成连接、资源浏览和下载；旧版只是不显示聊天入口和资源卡片。

## 0.4.x 程序存储位置与磁盘空间

### 目标

用户可以选择 ResourceManager 的程序数据目录，避免数据库、复制发布的资源、更新包和临时文件持续占用系统盘。首次使用时必须确认存储位置，之后可以在设置中迁移。

界面统一使用“存储位置”这个名称，因为其中既有可清理的缓存，也有数据库、发布副本等不可随意删除的数据。

### 0.4.0 存储目录基础

- [ ] 增加启动引导：首次打开时显示存储位置选择窗口，用户确认后再进入主界面。
- [ ] 列出本机可写的固定磁盘，并显示每个磁盘的总容量与剩余空间；允许手动选择具体文件夹。
- [ ] 默认建议 `%LOCALAPPDATA%\ResourceManager`，但不替用户自动确认。
- [ ] 在写入配置前验证目录可创建、可读写，且不是某个普通文件的子路径冲突。
- [ ] 使用一个很小的引导配置记录实际数据目录；数据库和大文件写入用户选择的位置。
- [ ] 将以下内容统一放入存储根目录：
  - SQLite 数据库及 WAL 文件；
  - “复制到软件管理目录”的发布副本；
  - 软件更新暂存包；
  - 日志；
  - 下载任务状态和软件内部临时缓存。
- [ ] 用户主动选择的下载目标继续保存在用户指定的位置，不强制放进程序存储目录。
- [ ] 下载目标旁的 `.rm-part` 仍跟随用户选择的目标目录，避免跨磁盘完成下载时再次复制整个文件；数据库中的断点状态放在程序存储目录。
- [ ] 所选磁盘断开、目录丢失或权限变化时，阻止服务带着空数据库启动，并给出重新选择或重试入口。

### 0.4.1 修改位置与安全迁移

- [ ] 设置页增加“存储位置”，显示当前绝对路径并允许更改。
- [ ] 检测旧版 `%LOCALAPPDATA%\ResourceManager` 数据；首次进入新版时提供迁移，而不是创建一套空数据。
- [ ] 迁移前计算所需空间，并在空间不足时停止操作。
- [ ] 迁移时暂停共享、下载和数据库写入，复制完成后核对文件数量、大小和数据库可打开性。
- [ ] 只有全部校验成功后才切换引导配置；失败时继续使用旧位置，不删除原数据。
- [ ] 切换成功后提示用户是否清理旧位置。清理必须由用户明确选择。
- [ ] 为迁移中断保留可恢复状态，避免断电后新旧目录都无法使用。

### 0.4.2 左下角磁盘空间状态

- [ ] 在左侧导航底部显示当前存储盘的信息：
  - `磁盘已用`：整个磁盘已经占用的空间；
  - `本程序`：ResourceManager 存储根目录的实际占用；
  - `剩余`：磁盘当前可用空间。
- [ ] 明确“本程序”是“磁盘已用”的一部分，三个数字不是相加关系。
- [ ] 使用容量条和简短文本呈现，鼠标悬停时显示存储路径、磁盘总容量和精确字节数。
- [ ] 程序目录大小在后台统计，不阻塞界面；发布副本、更新包或缓存变化后触发刷新。
- [ ] 大目录统计可取消并限制刷新频率，避免持续扫描磁盘。
- [ ] 剩余空间过低时使用醒目状态，并在发布副本、下载缓存和更新下载前再次检查。

### 验收场景

- [ ] 全新安装第一次启动必须确认位置；选择 D 盘后，重启仍使用同一目录。
- [ ] 从旧版升级可以完整迁移设备、收藏、发布、下载记录和发布副本。
- [ ] 迁移失败或空间不足时，原目录与原数据库保持可用。
- [ ] 左下角显示的磁盘已用、程序占用、剩余空间与 Windows 属性中的数据一致。
- [ ] 统计数十万文件时界面仍可操作。

## 0.5.x 资源树、分组与权限

### 目标

发布者可以把文件和文件夹放入分组，分组形成树状目录。远端看到同样的树。没有主动分组的资源全部归入“默认组”。分组可以设置公开、私有或设备白名单权限。

分组只组织发布入口，不移动“引用原位置”的真实文件，也不改变“复制副本”的内部保存规则。

### 0.5.0 分组与文件树

- [ ] 新增资源分组数据：分组 ID、名称、父分组、排序位置、创建时间。
- [ ] 支持多级分组；禁止循环父子关系、空名称和同级重名。
- [ ] 建立固定的“默认组”，不能删除；旧版本已经发布的资源迁移到默认组。
- [ ] 我的发布页面改为树状视图，支持创建、重命名、移动和删除分组。
- [ ] 资源可以在分组之间移动；移动只修改组织关系，不移动磁盘上的源文件。
- [ ] 删除非空分组前让用户选择把资源移到默认组或同时撤销发布。
- [ ] 远端资源清单返回相同树结构，并保持稳定排序。
- [ ] 收藏仍按资源 ID 定位；资源换组或分组改名后收藏不失效。

### 0.5.1 请求身份与权限执行

- [ ] 为每个远端请求建立可信的访问身份，不能只靠界面隐藏资源。
- [ ] 直连请求根据已握手的设备 ID 识别访问者；为后续服务器转发预留明确的来源设备身份。
- [ ] 资源目录、文件树和文件内容接口统一经过权限检查，避免知道资源 ID 后绕过目录直接下载。
- [ ] 设备 ID 不匹配、握手过期或来源无法确认时拒绝受限资源。
- [ ] 保留可读的拒绝原因，但不向无权限设备泄露私有资源的名称与存在状态。

### 0.5.2 分组权限与白名单

- [ ] 每个分组支持三种权限：
  - `公开`：所有已连接并完成身份握手的设备可见、可下载；
  - `私有`：只在本机显示，远端目录中完全不可见；
  - `白名单`：只有选中的设备 ID 可见、可下载。
- [ ] 默认组初始为公开，保持升级后现有共享行为不变。
- [ ] 白名单选择器显示设备昵称、设备 ID 和最近地址；昵称变化不影响授权。
- [ ] 子分组默认继承父分组权限，允许明确覆盖；界面显示权限来源。
- [ ] 移动资源或分组时立即按新权限生效。
- [ ] 删除设备时同步清理白名单引用，并提示受影响的分组数量。
- [ ] 收藏中的资源失去权限后显示“无权访问”，与“离线”和“资源已撤销”区分。

### 验收场景

- [ ] 未分组的旧资源全部出现在默认组，资源 ID 和收藏保持不变。
- [ ] 多级分组在发布端与访问端结构、顺序一致。
- [ ] 私有分组不会出现在任何远端响应中。
- [ ] 白名单设备可以浏览和下载，非白名单设备即使知道资源 ID 也无法获取内容。
- [ ] 设备改 IP 或昵称后，基于设备 ID 的白名单仍然有效。

## 0.6.x 多服务器连接、发布与上传

### 目标

左侧工作空间增加“服务器”。页面整体沿用设备页的布局，并增加一层标签页；每个标签对应一台已经绑定的 ResourceManager 服务器。

服务端第一版必须提供 **Linux x64 无界面版本**，面向云服务器、虚拟机和容器运行。服务端不能依赖 WPF、WinForms、Windows 注册表或其他 Windows 专用能力；部署和维护流程必须支持 AI 与自动化脚本非交互执行。

客户端可以：

- 绑定多台部署了 ResourceManager 服务端的服务器；
- 查看服务器维护的在线用户列表；
- 浏览同一服务器中其他用户允许访问的资源；
- 发布本机资源入口，文件内容仍由发布方电脑提供；
- 把资源上传到服务器，发布方离线后仍可从服务器下载。

### 0.6.0 服务器项目、协议与绑定

- [ ] 新增可独立部署的 `ResourceManager.Server` ASP.NET Core 项目。
- [ ] 服务端目标框架保持跨平台，正式产物至少包含自包含的 `linux-x64` 版本；代码结构为以后增加 `linux-arm64` 留出空间。
- [ ] 服务端以后台进程运行，不提供桌面图形界面；所有配置、初始化、升级和诊断均可通过命令行完成。
- [ ] 配置同时支持 JSON 配置文件、环境变量和命令行参数，并规定清晰的覆盖顺序，部署过程不依赖人工回答交互问题。
- [ ] 约定 Linux 路径：配置默认位于 `/etc/resourcemanager`，持久数据默认位于 `/var/lib/resourcemanager`，日志默认写入标准输出并由 journald 或容器收集；所有路径均允许覆盖。
- [ ] 提供稳定的 `--help`、`--version`、`check-config`、`doctor` 和数据库迁移命令；成功与失败使用稳定退出码，并输出可供脚本解析的错误信息。
- [ ] 服务端提供健康检查、协议版本和功能能力接口；客户端拒绝不兼容的普通网站或错误服务。
- [ ] 分开提供存活检查和就绪检查，便于 systemd、Docker 和部署脚本判断进程已启动且数据库、存储目录可用。
- [ ] 客户端保存多台服务器配置：服务器 ID、名称、HTTPS 地址、凭据、最后连接状态。
- [ ] 服务器页面支持添加、编辑、移除和重新连接服务器。
- [ ] 每台服务器对应一个标签页，标签显示名称、在线状态和错误摘要。
- [ ] 服务器配置与本地设备地址簿分开保存，移除服务器不删除本机发布资源。
- [ ] 服务端提供明确的数据目录、上传目录、最大容量和单文件限制配置。

### 0.6.1 身份、在线名单与服务器发现

- [ ] 客户端连接服务器时提交固定设备 ID、昵称、头像和客户端版本。
- [ ] 服务器维护当前在线设备名单，并向已连接客户端推送上线、资料变化和离线事件。
- [ ] 同一设备 ID 的重复连接、凭据撤销和服务器重启要有明确处理规则。
- [ ] 服务器至少支持访问令牌或邀请码，避免任何知道地址的人无条件进入；后续可扩展账号体系。
- [ ] 在线名单按设备 ID 去重，显示昵称、头像、在线状态和资源数量。
- [ ] 客户端断线自动重连；断线期间保留服务器标签和缓存目录，标为“服务器离线”。

### 0.6.2 “发布”模式

- [ ] 用户可以把本机资源或资源组发布到某台服务器的资源目录，但不上传文件内容。
- [ ] 服务器只保存资源元数据、所有者、权限、在线状态和下载路由。
- [ ] 发布者在线时，其他用户可以从发布者电脑获取内容；发布者离线时显示“发布者离线”。
- [ ] 资源变化、撤销、移动分组和权限变化同步到服务器目录。
- [ ] 断点续传、完整性校验和文件夹结构沿用现有下载模型。
- [ ] 在开始实现前确定传输路线：
  - 同网或地址可达时客户端直连发布者；
  - 跨网络是否允许服务器中继，或明确只显示“无法直连”。

### 0.6.3 “上传”模式

- [ ] 用户可以把文件或文件夹上传到服务器存储，上传完成后发布方离线仍可下载。
- [ ] 上传使用临时文件、分片或 Range 续传；完成后原子切换到正式文件。
- [ ] 服务端校验文件大小和内容哈希，失败时不发布不完整资源。
- [ ] 文件夹上传保留目录结构，并防止路径穿越、符号链接越界和非法文件名。
- [ ] 显示上传进度、暂停、继续、失败原因和删除任务。
- [ ] 服务器实施单用户配额、单资源限制、总容量预留和低磁盘保护。
- [ ] 删除已上传资源时同时处理服务器文件、资源目录、收藏状态和正在下载的连接。

### 0.6.4 服务器资源体验与运维

- [ ] 服务器标签内采用“用户列表 + 资源树”的双栏布局，并清楚区分“本机发布”和“已上传”。
- [ ] 收藏记录服务器 ID、所有者设备 ID、资源 ID 和资源模式，服务器之间不串数据。
- [ ] 下载列表标明来源是局域网设备、服务器发布者还是服务器存储。
- [ ] 服务器资源复用公开、私有、白名单权限；服务器必须在目录和内容接口同时执行权限。
- [ ] 服务端记录必要的审计信息：登录、上传、删除、权限变更和异常下载，不记录文件正文。
- [ ] 提供 Linux systemd 单元、Dockerfile、Docker Compose 示例，以及 HTTPS、备份、升级和数据恢复说明。
- [ ] 提供可重复执行的 Bash 部署脚本；重复执行不会覆盖已有密钥、配置或数据，失败时指出具体步骤和恢复办法。
- [ ] 所有部署步骤都能以非交互方式运行，敏感配置通过文件、环境变量或标准输入传入，不把令牌直接写进命令行历史和普通日志。
- [ ] 启动、迁移、备份和升级日志使用稳定字段与明确错误码，方便 AI 判断执行结果并继续处理。
- [ ] 服务端与客户端独立显示版本，协议不兼容时给出升级方向。

### 验收场景

- [ ] 客户端绑定两台服务器后出现两个独立标签，在线名单和资源互不混淆。
- [ ] 普通 HTTP 网站或协议不兼容的服务端不能被误绑定。
- [ ] 两个用户绑定同一服务器后能看到对方；一方离线后状态及时更新。
- [ ] “发布”的资源在发布者离线时不可下载，重新上线后恢复。
- [ ] “上传”的资源在上传者离线后仍可从服务器下载。
- [ ] 服务器下载保留文件夹结构并支持中断续传。
- [ ] 没有权限的用户不能从目录、猜测资源 ID 或直接内容地址绕过限制。
- [ ] 服务器磁盘空间不足、配额超限、网络中断和客户端版本不兼容时都有明确状态。
- [ ] 在全新的 Ubuntu/Debian x64 环境中，可以通过文档或脚本无图形界面完成安装、初始化、启动、健康检查、升级和卸载。
- [ ] systemd 和 Docker 两种部署方式都能自动重启服务，并将配置与持久数据放在可备份的宿主机目录中。

## 后置候选：GitHub 差分更新（版本待定）

### 启动条件

当前 Windows x64 自包含单文件约为 203 MB，但局域网内可以由可信设备发布最新完整版本。只有公网完整包的实际分发量、下载耗时或带宽成本成为明确问题时，才启动差分更新；该功能不再绑定 0.3.2，也不阻塞存储位置、权限和服务器路线。

### 发布与产物

- [ ] 先固定可重复的 Release 打包参数，验证相同提交在本机和 GitHub Actions 生成完全相同的 SHA-256，避免不稳定二进制放大补丁。
- [ ] 评估单文件压缩并记录压缩后的启动耗时、完整包大小和差分包大小；只有实际收益明确时才启用。
- [ ] GitHub Actions 构建当前完整 EXE 后，下载上一正式版本的完整 EXE 并生成 `上一版本 → 当前版本` 的二进制差分包。
- [ ] Release 始终上传完整 `ResourceManager.exe`；差分包使用包含起止版本的稳定名称，例如 `ResourceManager-上一版本-to-当前版本.patch`。
- [ ] 同时发布机器可读的更新清单，至少包含起止版本、旧 EXE SHA-256、新 EXE SHA-256、差分包 SHA-256、文件大小和下载地址。
- [ ] 更新清单和附件地址只能指向本项目对应 GitHub Release，沿用当前可信发布源约束。
- [ ] 如果差分包达到完整包大小的 60% 或更大，流水线不发布该差分包，客户端直接使用完整更新。

### 客户端更新流程

- [ ] 检查更新时先计算当前正在使用的 EXE SHA-256；只有版本和旧文件哈希都与更新清单一致时才允许使用差分包。
- [ ] 优先下载匹配当前版本的差分包；没有匹配补丁、用户跨版本升级或旧文件被修改时自动下载完整 EXE。
- [ ] 差分包和完整包都支持临时文件与断点续传；网络中断后继续已有进度，不从零重新下载。
- [ ] 大文件请求不再发送 `Cache-Control: no-cache`；仅最新版本元数据请求使用重新验证策略，并优先协商 HTTP/2 或更高协议。
- [ ] 在临时位置对旧 EXE 副本应用补丁，不修改正在运行的正式 EXE。
- [ ] 补丁生成的新 EXE 必须同时通过目标文件大小、SHA-256、`MZ` 文件头和目标版本检查；任一检查失败时删除临时结果并自动回退完整包。
- [ ] 所有校验通过后继续沿用当前退出旧进程、原子替换和重新启动流程；数据库、设备 ID、发布、收藏和下载任务保持不变。
- [ ] 更新界面显示下载方式、已下载大小、实时速度和预计剩余时间，并明确标记“差分更新”或“完整更新”。

### 第一版支持范围

- [ ] 只保证从最新上一正式版本升级到当前目标版本，不串联多个历史补丁。
- [ ] 从更早版本直接升级时使用完整包。
- [ ] 保留桌面手工下载完整 EXE 的方式，差分系统故障不能阻止用户正常安装最新版。
- [ ] 差分更新仍允许短暂重启程序，不做 WPF 进程内代码热替换。

### 验收场景

- [ ] 从上一正式版本升级时选择差分包，实际下载量明显小于完整包，并生成与云端完整 EXE SHA-256 完全一致的文件。
- [ ] 当前 EXE 哈希不匹配、补丁损坏、补丁应用失败和新 EXE 校验失败时，旧程序保持可用并自动切换完整包。
- [ ] 差分下载和完整下载中断后均可续传，关闭窗口到托盘不会取消后台更新。

## 开始实现前需要逐项确认的选择

这些问题不阻塞记录需求，但进入对应版本前需要确定：

1. 存储位置是否包含日志和更新暂存包。当前建议包含，系统盘只保留很小的目录指针。
2. 资源分组是否允许无限层级。当前建议支持多级，但界面限制常用操作保持简单。
3. 白名单是否只授权设备，还是未来也支持服务器账号和用户组。0.5.x 先按设备 ID，服务器阶段再扩展主体类型。
4. 服务器“发布”资源在双方无法直连时，是允许服务器中继，还是明确不可下载。该选择决定服务端带宽成本和协议复杂度。
5. 服务器采用邀请码、长期访问令牌还是账号密码。当前建议第一版使用服务器签发的设备令牌。
6. 已上传资源的配额、保留期限、重复文件处理和管理员删除规则。
7. 反馈提交渠道使用自建接口、GitHub Issues 中转还是其他服务。当前建议客户端依赖抽象提交接口，并始终保留本地导出反馈包。
8. Git 协同第一版采用 Git bundle、临时只读 Git 服务还是工作树快照。当前建议 Git bundle，边界清楚且不需要在客户端托管写操作。
9. 局域网聊天未来是否需要服务器离线消息、跨设备历史同步和端到端加密。0.3.6 第一版建议只做在线点对点消息与本机历史。

## 暂不纳入以上版本

- 公网 NAT 打洞；
- 多服务器联邦；
- 端到端加密；
- 自动把发布资源同步成多设备副本；
- 未经用户确认的旧数据自动删除。
